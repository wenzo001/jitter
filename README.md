# Jitter

Jitter 是一个常驻本机的定时小工具：把浏览器里「复制为 cURL」得到的命令粘进来，设定执行时间，到点自动发出 HTTP 请求；判定成功后还可以再发一条通知 curl。任务、日志、统计全部只存在你自己的电脑上。

适合谁用：想「每天某个时段自动做一次请求」的人（打卡、签到、领券、报数），以及想「每隔 N 分钟 / 小时轮询一次接口、按返回内容决定要不要通知自己」的人。

当前版本：2.1.11

## 能做什么

- 粘贴 curl 直接用，也可以改用表单填 URL / 方法 / 请求头 / 请求体
- 三种执行节奏：每天在时段内随机一次、每天准点（可前后浮动几分钟）、每隔 N 秒 / 分钟 / 小时 / 天循环
- 成功判定可自定义：默认任意 2xx 就算成功，也可以指定状态码、精确匹配响应体，或写条件表达式
- 命中成功条件后可以再发一条通知 curl（企业微信 / 钉钉 / Telegram / 自建 Webhook 都行，只要是 curl）
- 执行条件：只在指定星期、时段、工作日 / 休息日、接通电源、指定本机 IP 时才执行
- 中国法定节假日日历（含调休上班日），可按工作日 / 休息日安排任务
- 执行记录、统计报表、只读数据库浏览、备份 / 导出 / 恢复
- Windows 托盘常驻、三平台开机自启、应用内检查升级

## 快速开始

### 1. 下载

到 Releases 页面下载与你的系统对应的压缩包（<https://github.com/wenzo001/jitter/releases>）：

| 系统 | 压缩包 | 包内程序 |
| --- | --- | --- |
| Windows 64 位 | `jitter-windows-x64.zip` | `jitter.exe` |
| macOS Apple 芯片 | `jitter-macos-arm64.zip` | `jitter` |
| macOS Intel | `jitter-macos-x64.zip` | `jitter` |
| Linux x86_64 | `jitter-linux-x64.zip` | `jitter` |
| Linux arm64 | `jitter-linux-arm64.zip` | `jitter` |

解压后得到一个单文件程序，没有额外依赖。macOS 首次运行若提示「无法验证开发者」，在「系统设置 → 隐私与安全性」里点「仍要打开」。

### 2. 启动

- Windows：双击 `jitter.exe`。发布版不弹控制台窗口，程序在右下角托盘常驻；托盘菜单有「打开界面 / 重启 / 开机自启 / 退出」。再双击一次不会启动第二份，只会用浏览器打开已有实例的页面。
- macOS / Linux：终端里运行 `./jitter`（需要可执行权限：`chmod +x jitter`），然后用浏览器访问 `http://127.0.0.1:3000`。这两个平台目前没有托盘图标，退出请在网页里点「设置 → 退出 → 退出 Jitter」，或直接结束进程。

默认端口是 3000。如果端口被占用，程序会自动往后找可用端口（最多尝试 100 个），实际地址以「设置 → 常规 → 运行信息 → 访问地址」为准。

### 3. 建第一个任务

1. 点顶栏的「试跑 curl」，把从浏览器复制的 curl 命令粘进去，点「运行」，确认请求能通、能拿到预期响应。试跑不会写进执行记录。
2. 点左侧「新建任务」，在第 1 段「请求」里粘上同一条 curl（也可以切换成手填 URL / 方法 / 头 / 体）。
3. 在第 2 段「执行时间」里选节奏：每天在某个时段内随机一次，或每隔 N 分钟循环。表单下方会直接列出「接下来 7 次执行」的时刻，方便核对。
4. 需要的话再填第 3 段「成功与通知」（判定标准、通知 curl）和第 4 段「执行条件」，点「创建任务」。

任务默认立即生效，调度器会在下一个符合条件的时间点执行它。

### 平台差异

| 能力 | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 托盘图标（打开界面 / 重启 / 退出） | 有 | 暂无 | 暂无 |
| 开机自启 | 有 | 有 | 有 |
| 界面地址 | `http://127.0.0.1:<端口>` | 同左 | 同左 |

开机自启是写文件的方式实现的（Windows 写启动目录的 `.cmd`，macOS 写 LaunchAgents 的 `.plist`，Linux 写 `~/.config/autostart` 的 `.desktop`），在「设置 → 常规 → 开机自启」里开关。从源码运行时这一项不可用。

## 界面导览

整个界面只有这一页，分成顶栏、左侧任务列表、右侧执行记录三块，加上若干弹窗。布局以电脑端为主（大屏会铺满可用宽度，不留大片空白），窄到平板宽度时会自动折叠顶栏、收窄侧栏，手机上则改成上下堆叠。

### 顶栏

顶栏只留电脑端每天真正常用的东西，从左到右：

- 品牌名与版本号，副标题是「先测通，再定时 · 按秒 / 分 / 时 / 天调用 curl」（窗口变窄时副标题自动隐藏）。
- 状态行：显示最近一次操作的结果，失败时为红色。没有消息时这一块是空的，不占视觉重量。
- 实时时钟：时间、日期、星期，以及当天的标签（工作日 / 休息日 / 法定节假日 / 调休上班）。点它可以打开日历弹窗，看整月的放假与调休安排。
- 操作区：统计摘要（今日执行次数、近 7 天成功率、近 7 天平均耗时、正在执行中的任务数）、主按钮「试跑 curl」，以及「更多」下拉。

「更多」下拉里放着低频入口：统计、数据库、运行日志、诊断、设置，以及语言切换「中文 / English」（当前语言前面带 ✓）。

窗口变窄时顶栏会自动折叠：先收掉副标题，再收掉统计摘要，最后分成两段排布，不会从中间断开。

### 语言（中文 / English）

顶栏「更多 → 中文 / English」可以随时切换界面语言，切换后立刻生效并记住选择（下次打开还是这个语言）。

- 界面文案、按钮、提示、错误说明都是中英双份，切换后立即生效。
- **来自后台的数据不翻译**：任务名、调度描述（如「每天 09:45–09:58 随机一次」）、执行记录里的响应内容、后台返回的错误原文都保持原样。也就是说英文界面下仍会看到中文的任务名和调度描述，这是有意为之——这些是你自己写的数据，翻译反而容易对不上。


### 左侧：任务列表

标题栏显示任务数量，右侧有「新建任务」和「刷新」。

每张任务卡片包含：

- 任务名称、请求方法与 URL、调度描述（如「每天 09:00–18:00 随机一次」「每 30 分钟（从 09-01 08:30 起算）」）。
- 「上一次执行」标记：单行显示 `成功` / `未满足成功条件` / `失败` 的标签加一句「几小时前」「几天前」。鼠标悬停会给出完整信息（准确时刻、触发来源、状态码、耗时），卡片本身不再换行堆字。
- 暂停状态、跨午夜标记、请求超时标记。
- 底部一行说明下次执行时间；调度已停用时显示「调度已停用，历史记录保留」。
- 左侧的拖拽把手：拖动可以调整顺序，也可以聚焦后用 ↑ / ↓ 键调整。
- 右上角按钮：「立即执行」（真实发一次请求，会写执行记录）、「编辑」，以及「更多」菜单：试跑（不记录）、暂停几天 / 调整暂停 / 取消暂停、停止调度 / 启用调度、删除任务。

「暂停几天」最多 15 天，可以选「今天起算」（今天剩余时间一律不再触发）或「明天起算」（今天照常执行）。暂停期间执行记录会保留。

### 右侧：执行记录

显示当前选中任务的历次执行，顶部有「清理日志」「刷新」和「加载更早」。最新的一次在最上面。

每条记录的一行是：任务、时间、耗时、请求方式 + URL、状态标签（HTTP 状态、是否成功、是否已通知），末尾是「详情 ›」。状态标签统一排在请求地址**后面**，一眼能顺着「做了什么 → 结果如何」读下去；地址太长会省略，悬停可看全文。

点开可以看到完整内容：请求方法与 URL、请求头、请求体、响应状态码、响应头、响应体、耗时、错误信息。响应体超过 `logBodyLimitBytes`（默认 100 KB）会被截断，截断时记录里有明确标记，此时按响应体做的判定不会成立。

如果这条执行发过通知，**通知的详情固定排在详情的最下面**，单独分成「通知详情」一节（带「已发送 / 失败」状态和一句说明），和上面的任务执行记录分开看，不会混在一起。

请求头、请求体、响应头、响应体里的内容会按类型渲染：

- **JSON**：自动缩进排版（2 空格）并按 JSON 语法高亮，一眼看到字段层级。
- **脚本类内容**（curl、bash、shell、python、sql、yaml、xml…）：按对应语言高亮。
- **其它**：按纯文本显示。

全部用等宽字体（JetBrains Mono）渲染，长行自动折行，不会被截掉。

### 任务表单弹窗

点「新建任务」或「编辑」打开，分四段：

**1. 请求**

- 任务名称（必填，最多 200 字）。
- 请求填写方式：`curl` 或 `结构化`。选 curl 时粘一整条命令即可；选结构化时填 URL、方法、Headers（每行一个 `名称: 值`）、Body。
- 旁边有「先试跑」按钮：拿当前这份配置去测试台跑一次，确认能通再保存。

**2. 执行时间**

- 执行方式：`定时执行`（每天一次）或 `循环执行`（每隔一段时间）。
- 定时执行分三种形态：时段（开始 + 结束，在区间内随机挑一个时刻）、精确时间（每天就在这个点）、精确时间 + 前后浮动（以该时间为中心前后各随机浮动 N 分钟，最多 60 分钟）。
- 循环执行：每隔 N 秒 / 分钟 / 小时 / 天；「第一次执行时间」留空表示从现在开始算，填了就以它为锚点对齐（例如从 09:00 起每 2 小时）；还可加 0–N 秒随机抖动。
- 跨午夜说明：时段结束早于开始表示跨午夜（例如 23:50–00:10），仍算作开始那天的一次。
- 下方会显示「接下来 7 次执行」的时刻预览。
- 「电脑启动后自动执行一次」开关：默认关闭，只对当前任务生效。程序启动后会延迟 15 秒等网络就绪，再对勾选了该开关的任务各执行一次，同样检查执行条件。

**3. 成功与通知**

- 成功条件（默认折叠）：期望状态码、期望响应体（完全相等）、条件表达式。三项都不填时，任意 2xx 视为成功；填了则需全部满足；只填表达式时不会额外限制 2xx。
- 条件表达式是受限的类 JS 表达式，不执行任意代码，支持 `=` / `==` / `!=` / `>` / `<`、`&&` / `||` / `!`、三元运算符，以及 `$status`、`$body`、`$json` 三个变量；响应体按 JSON 解析后可用 `data.result.remindtype=0` 这样的路径取值，路径取不到一律按不成立处理。
- 「成功时发送通知」开关，打开后必须填一条通知 curl。只有判定成功才发送；通知本身失败只记录它自己的结果，不会影响任务本身。

**4. 执行条件（可选）**

打开「只在满足条件时执行」后才会显示这些字段，详见下面的「执行条件」一节。条件不满足时本次执行会被跳过，跳过原因写进执行记录。

### 测试台

顶栏「试跑 curl」打开，也可以从任务表单或任务卡片的「更多 → 试跑」进入。它会按顺序给出一串步骤，每步标注通过 / 失败 / 跳过和耗时，并可展开查看该步的请求与响应原文：

1. 解析 curl
2. 本地条件（星期 / 时段 / 工作日 / 休息日）
3. 电源 / 本机 IP 条件
4. 条件检查（前置 curl）
5. 主请求
6. 成功条件判定
7. 发送通知

任何一步不通过，后面的步骤会被标记为「跳过」并给出原因。试跑不会写进执行记录；如果是在某个已有任务上试跑，会在该任务下留一条测试记录（可在数据库弹窗里查看）。

### 统计弹窗

显示任务总数与启用数、正在执行数、今日执行次数、近 7 天执行次数、近 7 天成功率、近 7 天平均耗时，以及每个任务的最近状态与成功率。

### 日历弹窗

按月展示每一天的归类：工作日、休息日、法定节假日、调休上班；点顶栏时钟进入。右上角可以切换年份和月份。

**调休上班日按工作日算**：它落在周末，但实际上是上班日，所以格子里主标签是「工作」，下面另起一行小字标注「调休 · 节日名」；图例里的「工作日」计数也已经包含调休日，「调休上班 N」单独标出来并附带说明。

表头的星期和下面的日期列是对齐的：星期写在这一列最上面，日期数字跟它左对齐。

日历只有「月」一种视图——整年网格和这里的按天标注对不上，所以没有年视图。

### 数据库弹窗

只读浏览数据库：顶部列出所有表及各自的行数，选择表后可分页查看每一行的原始值。用于排查「数据到底存成什么样」，不能修改。

### 运行日志弹窗

顶栏「更多 → 运行日志」打开，用来回看程序自身的运行日志（按天一个文件）。上半部分是日志目录、保留天数和文件列表，选中某一天后可以查看内容、复制；大文件按字节分段读取，可以「加载更多」往后读，也可以回到开头。

### 诊断弹窗

顶栏「更多 → 诊断」打开，用来回答「现在是什么状态、哪里出了问题、下一步该做什么」：

- 顶部横幅给出服务状态和下一步建议（正常 / 降级 / 异常分别对应不同提示）。
- 运行信息：版本、已运行时长、数据库路径与是否可读写、运行日志目录、服务端最近一次错误。
- 「页面捕获到的异常」：列出页面上出现过的报错及其建议，可以「重新检测」「复制诊断信息」（直接发给维护者）「查看运行日志」「清空」。每条异常都带「技术详情（调用栈）」，复制诊断信息时也会一并带上，方便定位问题。

页面某个区域渲染出错时不会整页白屏，而是就地显示可读说明，并提供重试、复制详情、打开诊断面板三个动作。

后台整个没响应时（不是某个接口失败），页面顶部会出现红色横幅，写明「后台没响应」以及该怎么做（确认托盘图标还在、稍等重试、仍不行就重启 Jitter），并给出「重新检测」「查看运行日志」两个按钮；重启后调度会自动恢复。


### 设置弹窗

四个标签页：

- **常规**：日志保留天数、默认跳过 TLS 证书校验、接通电源时防止系统休眠、开机自启开关；节假日数据的年份列表与「立即拉取（去年 / 今年 / 明年）」按钮；运行信息（版本、运行模式、访问地址、安装目录、数据文件、开机自启文件路径）。
- **备份**：新建备份、导入 `.db` 备份、备份列表（可下载、恢复、删除）。
- **更新**：检查更新、下载并安装新版本。
- **退出**：退出 Jitter。

## 常见用法

### 每天定时打卡

1. 在浏览器里打开目标页面，按 F12 → Network → 找到那个请求 → 右键「Copy as cURL」。
2. 顶栏「试跑 curl」粘进去跑一次，确认能拿到成功响应。
3. 新建任务，第 1 段粘 curl；第 2 段选「定时执行 → 时段」，例如 08:30–09:30，每天在这个区间内随机挑一个时刻执行，避免每次都卡在整点。
4. 第 3 段按需加成功条件（例如接口返回 `{"code":0}`）和通知 curl。
5. 想让它只在工作日跑，就在第 4 段选「仅工作日」。

### 循环轮询

适合盯着一个会变的状态（库存、抢票、监控告警）。

1. 第 2 段选「循环执行」，每隔 5 分钟，单位选「分钟」。
2. 想要固定节奏就把「第一次执行时间」填成例如今天 09:00，之后始终是 09:00 / 09:05 / 09:10 这样对齐；留空则从保存那一刻起算。
3. 第 3 段用条件表达式判断结果，例如 `data.stock > 0`；配合通知 curl，一旦有货就给自己发一条消息。

### 自定义成功条件与通知

- 只要状态码对：第 3 段填「期望状态码」`200`。
- 要精确匹配：填「期望响应体」，内容必须与响应体完全一致。
- 要看 JSON 里的某个字段：填「条件表达式」，例如 `data.result.remindtype=0`；`$status` 是状态码，`$body` 是响应体原文。
- 三项可以叠加，需要同时满足。
- 「成功时发送通知」打开后填通知 curl，例如一条推送到机器人 Webhook 的 POST。通知只在判定成功时发出。

## 执行条件

执行条件是「执行前先判断，合适才发请求」。所有条件同时启用时，需要全部满足；不满足会跳过本次并在执行记录里写明原因。任务卡片上的「立即执行」是人工触发，不受执行条件限制。

| 条件 | 判定依据 | 前置条件与说明 |
| --- | --- | --- |
| 允许的星期 | 本地时钟的星期（0 = 周日） | 不选 = 每天都执行 |
| 执行时段 | 本地时钟，分钟精度 | 开始和结束要同时填且不能相同；结束早于开始表示跨午夜，按开始那天归属 |
| 仅工作日 / 仅休息日 | 中国法定节假日数据（含调休上班日） | 需要对应年份的节假日数据；数据缺失时该条件被跳过，并在记录里注明 |
| 只在接通电源时执行 | 本机电源状态 | 读不到电源状态时判定为不执行 |
| 只在本地 IP 匹配时执行 | 本机各网卡的 IP | 模式里 `*` 匹配任意数字或点，多组用逗号分隔，任意一组命中即可；例如 `10.1.*` 或 `192.168.*,10.*` |
| 条件检查 curl | 先发这个请求，再看下面的判定 | 填了「期望状态码」或「表达式」时必须同时填这条 curl |

注意「仅工作日 / 仅休息日」依赖节假日数据。数据来自 holiday-cn，在启动时静默拉取去年、今年、明年，每月 1 号自动刷新；拉取失败不会影响其它功能，只是这两个条件暂时无法判断。在「设置 → 常规 → 节假日数据」里可以手动拉取，并点开某一年的「查看明细」看具体哪天放假、哪天调休上班。

## 数据与备份

### 数据放在哪

以「数据文件」为准（「设置 → 常规 → 运行信息 → 数据文件」），默认是**程序所在目录**下的 `data/app.db`：

```
data/
  app.db            SQLite 数据库（任务、执行记录、测试记录、设置、节假日数据）
  logs/             程序运行日志：jitter-YYYY-MM-DD.log
  backups/          备份文件：jitter-YYYYMMDD-HHMMSS.db
```

> 数据目录跟**程序所在目录**走，不跟「你当时在哪个文件夹敲的命令」走。
> 在任何地方启动同一个程序，用的都是同一个 `data/`；把 `jitter.exe` 复制到别的文件夹再启动，那份数据就跟着 exe 走。
> 配置文件里写了 `dbPath` 时，相对路径按**配置文件所在目录**解析（绝对路径原样使用）。

数据库里的表：`tasks`（任务）、`logs`（执行记录）、`test_runs`（测试记录）、`settings`（全局设置）、`holiday_years`（节假日数据）。

### 备份、导出与恢复

「设置 → 备份」页：

- **新建备份**：对正在使用的数据库做完整快照（会正确合并 WAL），不会中断正在执行的任务。备份包含任务、日志和设置。
- **下载**：把某个备份导出成 `.db` 文件另存到别处。
- **导入 `.db` 备份**：选一个本地 `.db` 文件上传。
- **恢复**：用某个备份覆盖当前数据。恢复前会自动另存一份当前状态，误操作还能回退。
- **删除**：删掉不再需要的备份。

### 日志保留策略

这里有两种「日志」，别混淆：

| 类型 | 位置 | 保留策略 |
| --- | --- | --- |
| 执行记录（每次请求的结果） | 右侧面板、数据库 `logs` 表 | 「设置 → 常规 → 日志保留」设置天数，默认 30 天；超期的记录不查询、不渲染，并由后台巡检分批删除 |
| 运行日志（程序自身排错） | `logs/jitter-YYYY-MM-DD.log`，网页「运行日志」面板也能回看 | 按天一个文件，保留天数由环境变量 `JITTER_LOG_DAYS` 控制，默认 14 天 |

「执行记录 → 清理日志」弹窗可以按档位（10 / 30 / 180 / 365 天）预览并删除，删之前会先告诉你会删掉多少条、释放多少空间，也可以选择全部清空。配置文件里的 `logMaxRowsPerTask` 还能限制每个任务最多保留多少条记录（默认 0 = 不限制）。

### 节假日数据

存放在数据库的 `holiday_years` 表里。启动时静默更新一次，每月 1 号再自动刷新一次，范围是去年、今年、明年。「设置 → 常规 → 节假日数据」里可以随时手动拉取，并点开某一年的「查看明细」看具体哪天放假、哪天调休上班。

## 常见问题 / 故障排查

### 网页打不开

1. **先点顶栏「更多 → 诊断」**：它会告诉你服务状态、数据库是否可读写、运行日志目录和服务端最近一次错误，并给出下一步建议。
2. **端口被占用**：默认会自动往后找可用端口。实际地址看「设置 → 常规 → 运行信息 → 访问地址」，或运行日志里的 `Jitter 已启动: http://127.0.0.1:<端口>`。如果在配置文件里把 `autoIncrementPort` 关掉了，而端口又被占用，程序会启动失败并弹窗提示。
3. **macOS / Linux 没有托盘**：程序不会自动弹浏览器，请手动访问 `http://127.0.0.1:<端口>`。
4. **重复启动**：同一时间只允许一个实例运行。再次双击只会打开已有实例的页面，不会起第二份调度器。
5. **启动失败弹窗**：Windows 上启动失败会弹窗，里面列了要检查的三件事——数据库文件是否被占用或无写入权限、配置文件是否合法、端口是否被占用，并给出当天日志文件的路径。
6. **看到「界面文件缺失」提示页**：说明程序本体正常，但打包时没带上网页资源（缺少 `web/dist`），后台与调度器仍在正常运行。重新下载安装一次即可；自己构建的话，先在 `web/` 目录执行 `bun install && bun run build`，再回 `rust/` 执行 `cargo build --release -p jitter-app`。

### 任务不执行

按这个顺序排查：

1. **调度被停用**：任务卡片「更多 → 停止调度」会停掉自动执行，记录保留，用「启用调度」恢复。
2. **处在暂停区间**：卡片上会显示暂停起止时间；用「更多 → 取消暂停」提前结束。
3. **执行条件不满足**：跳过会在执行记录里留下原因（例如「当前 09:12 不在执行时段 10:00–12:00 内」「今天是周日，不在允许执行的星期内」「本机 IP（192.168.1.5）不匹配条件 10.*」）。
4. **错过了执行窗口**：电脑在窗口时间内处于关机 / 睡眠，窗口过去后不会补跑这次（循环任务迟到超过 60 秒也按错过处理，不会把积压的几次一次性重放）。
5. **节假日条件被跳过**：当年没有节假日数据时，「仅工作日 / 仅休息日」不参与判定，会在记录里注明。

### 请求失败

- **代理**：在 curl 里加 `-x http://代理:端口`（显式指定的代理不会被改写）；没写时才会用系统环境变量 `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY`，环境代理会先用 8 秒探测超时快速失败，再回退直连。
- **证书**：默认跳过 TLS 证书校验（对自签名证书的内网接口有用），可在「设置 → 常规」关掉。curl 里 `-k` 强制跳过、`--no-insecure` 强制校验。
- **超时**：默认 30 秒（配置项 `requestTimeoutMs`）。curl 里 `-m 10` / `--connect-timeout` 可以对单条请求覆盖。表单里把 `requestTimeoutMs` 设为 0 表示不设超时。
- **网络**：连接被重置这类错误在响应到达前会自动重试；其它错误直接记进执行记录。

### 日志在哪

- 程序自身的运行日志：与数据库同级的 `logs/` 目录，文件名 `jitter-YYYY-MM-DD.log`，默认保留 14 天。里面能看到启动、端口、任务调度、错误等关键信息。不想翻文件的话，顶栏「更多 → 运行日志」面板可以直接在网页里回看、复制。
- 每次请求的执行记录：网页右侧面板；也可以在「数据库」弹窗里看 `logs` 表。
- 备份：`backups/` 目录。

### 升级失败

- 检查更新需要能访问 GitHub Releases API（`api.github.com`），被网络或代理挡住时会显示错误信息。
- 每个版本的安装包名固定为 `jitter-<platform>-<arch>.zip`。如果该版本没有提供你当前平台对应的包，会提示「该版本没有提供 …」。
- Windows 上运行中的程序不能直接被覆盖，升级由一个辅助脚本在进程退出后替换文件并重启；这一步失败时旧程序仍然可用。
- 升级遗留的 `.old` 文件会在下次启动时自动清理。

### 卸载

1. 「设置 → 常规 → 开机自启」关掉开机自启。
2. 「设置 → 退出 → 退出 Jitter」退出程序。
3. 删掉程序文件。
4. 删掉数据目录（`data/`，包含 `app.db`、`logs/`、`backups/`）。想保留数据就先备份再删。

## 隐私与安全

- **数据全在本地**：任务、请求头、请求体、响应体、执行记录都存在本机 SQLite 数据库里，Jitter 不做任何遥测、不上传任何数据。
- **唯一会主动联网的地方**：拉取中国法定节假日数据（holiday-cn，来源是 GitHub raw 与 jsDelivr 镜像），以及检查升级时访问 GitHub Releases API。除此之外的对外请求全部是你自己配置的 curl 发出的。
- **默认只监听本机**：默认监听 `127.0.0.1`，局域网里其他设备访问不到。若把 `host` 改成 `0.0.0.0`，同网段的人就能打开这个界面、看到你的请求内容、修改并触发你的任务，请谨慎。
- **通知 curl 由你自己配置**：通知内容会发给你指定的服务端，请自行确认里面放了什么（不要把密钥写进会外发的通知正文）。
- **TLS 校验默认关闭**：这是为了兼容内网自签名证书，代价是失去了中间人防护。如果请求涉及账号、令牌或个人信息，建议在「设置 → 常规」里关掉「默认跳过 TLS 证书校验」，让证书校验恢复。
- **curl 里的密钥会明文存库**：请求头里的 `Authorization` 等内容会原样保存在数据库和执行记录里，请把数据目录当作敏感文件保管。

## 开发者说明

### 源码结构

```
rust/
  crates/jitter-core/   核心库：配置、数据库、调度、curl 解析、执行器、条件、节假日、备份、升级、日志
  crates/jitter-app/    可执行程序：HTTP 接口（api.rs）、调度器（scheduler.rs）、托盘（tray.rs）
web/                   前端（Vue 3 + TypeScript + antdv-next + Vite + Pinia + vue-i18n + vueuse），产物 web/dist
```

发布版是 Rust 版：`web/dist` 通过 `include_dir!` 编译进二进制，产出单文件程序。仓库里只保留这一条主线，早期的 TypeScript 版实现已彻底移除。

前端只依赖成熟的开源库，不自己造轮子：

- `antdv-next`：界面组件（按钮、弹窗、表格等），按需自动引入，构建时 tree shaking。
- `vue-i18n`：中英双语文案，两份文案的 key 用类型约束保持一致；新增文案时两份一起改。
- `@vueuse/core`：定时器、剪贴板、本地存储、页面可见性等通用能力。
- `pinia`：状态管理。

### 本地构建

```bash
cd web && bun install && bun run build          # 产物 web/dist，必须先生成
cd rust && cargo build --release -p jitter-app  # 产物 rust/target/release/jitter(.exe)
```

Windows 本机编译建议加两个参数，否则可能因为页面文件不足报「元数据损坏 / os error 1455」：

```bash
set CARGO_PROFILE_DEV_DEBUG=0
cargo build --release -p jitter-app --jobs 1
```

### 本地开发实例不会碰你的正式数据

开发时在仓库里跑起来的 Jitter，和你安装版 Jitter 是**两套完全独立的数据**：

| | 安装版 | 开发版（仓库里跑） |
| --- | --- | --- |
| 端口 | 3000 | 3111 |
| 数据库 | `<程序目录>/data/app.db` | `<仓库>/.tmp/dev/app.db` |
| 运行日志 | `<程序目录>/data/logs/` | `<仓库>/.tmp/dev/logs/` |

规则是这样定的（`rust/crates/jitter-core/src/config.rs`）：

- 相对 `dbPath` 按「**配置文件所在目录 → 可执行文件所在目录 → 当前工作目录**」解析，**不再跟当前工作目录走**。
  这是为了避免"在源码仓库根目录跑开发版，相对的 `data/app.db` 直接命中正式库"这种事故。
- 仓库根的 `jitter.config.json` 是**开发 / 容器用的默认配置**：`dbPath` 指向 `.tmp/dev/app.db`，`port` 是 3111。
- Docker 用 `JITTER_DB_PATH` / `PORT` 环境变量覆盖，行为不变。
- 想同时跑两个实例，设 `JITTER_ALLOW_MULTI_INSTANCE=1`。

启动后可以在「设置 → 常规 → 运行信息 → 数据文件」或 `/api/health` 的 `dbPath` 字段确认当前连的是哪个库。

### 测试

```bash
cd rust && cargo test -p jitter-core --jobs 1
cd web && bun run typecheck && bun run test && bun run build
```

前端测试里有一条会逐条用 `vue-i18n` 官方编译器编译中英文案：**文案里不能出现裸的 `|`**（vue-i18n 把它当复数分隔符，会导致用到该文案的组件渲染失败）。改文案后一定要跑 `bun run test`。

### 环境变量

| 变量 | 作用 | 默认值 |
| --- | --- | --- |
| `PORT` | 覆盖监听端口 | 3000 |
| `HOST` | 覆盖监听地址 | `127.0.0.1` |
| `JITTER_DB_PATH` | 覆盖数据库路径（同时决定 `logs/` 与 `backups/` 的位置） | `data/app.db` |
| `JITTER_CONFIG` | 指定配置文件路径 | 按「启动目录 → 可执行文件旁」查找 `jitter.config.json` |
| `JITTER_ALLOW_MULTI_INSTANCE` | 设为 `1` 允许同时运行多个实例（默认只允许一个） | 关闭 |
| `JITTER_STARTUP_DELAY_MS` | 启动前等待的毫秒数，用于升级 / 重启后等旧进程退出（上限 10000） | 0 |
| `JITTER_LOG_DAYS` | 运行日志文件保留天数（1–365） | 14 |
| `JITTER_UPDATE_REPO` | 检查升级使用的 GitHub 仓库 | `wenzo001/jitter` |
| `RUST_LOG` | 日志过滤级别 | `info` |

### 配置文件 `jitter.config.json`

| 字段 | 含义 | 默认值 |
| --- | --- | --- |
| `port` | 监听端口 | 3000 |
| `host` | 监听地址 | `127.0.0.1` |
| `autoIncrementPort` | 端口被占用时自动往后找 | true |
| `portMaxAttempts` | 最多尝试多少个端口 | 100 |
| `dbPath` | 数据库路径 | `data/app.db` |
| `logBodyLimitBytes` | 响应体记录上限（超出截断，截断时按响应体的判定不成立） | 102400 |
| `logsPageSize` | 执行记录每页条数 | 50 |
| `logsMaxPageSize` | 每页条数上限（不能小于 `logsPageSize`） | 200 |
| `requestTimeoutMs` | 请求超时毫秒数，0 表示不设超时 | 30000 |
| `logRetentionDays` | 执行记录保留天数 | 30 |
| `logMaxRowsPerTask` | 每个任务最多保留的记录条数，0 表示不限制 | 0 |
| `shutdownGraceMs` | 退出前留给在途执行的收尾时间（毫秒） | 150 |
| `defaultWindowMinutes` | 默认时间窗口分钟数 | 5 |
| `pollIntervalMs` | 前端轮询间隔毫秒数 | 4000 |

优先级：内置默认值 < 配置文件 < 环境变量。配置文件查找顺序：显式指定 > `JITTER_CONFIG` > 启动目录 > 可执行文件旁。

`dbPath` 写相对路径时按「配置文件所在目录 → 可执行文件所在目录 → 当前工作目录」解析；写绝对路径就原样使用。

### 发布产物与升级契约

- 每个平台打一个压缩包，资产名必须保持 `jitter-<platform>-<arch>.zip`（`platform` ∈ `windows` / `macos` / `linux`，`arch` ∈ `x64` / `arm64`）。内置升级逻辑按这个名字找当前平台的安装包，改名会让升级找不到包。
- 压缩包内只有一个可执行文件：Windows 是 `jitter.exe`，macOS / Linux 是 `jitter`。
- 同时发布同名 `.sha256` 校验文件。
- 触发方式是打 `v*` 标签；流水线会先跑两边的测试再打包。

### 接口契约

前端请求路径与后端路由是一一对应的契约，改动必须同步：

| 位置 | 作用 |
| --- | --- |
| `web/src/api/*.ts` | 前端发起请求的封装（tasks / logs / system / backup / metrics / database / testbench） |
| `rust/crates/jitter-app/src/api.rs` | 后端路由与 JSON 字段 |

`web/src/api/client.ts` 统一走相对路径 `/api/...`，由同一个二进制提供接口与静态页面。

## 文档与代码同步约定

- **接口路径与 JSON 字段是契约**。改动任何 `/api/*` 路径或字段名时，必须同时更新前端 `web/src/api/*` 与后端 `rust/crates/jitter-app/src/api.rs`，并确认 `web/src/types/*` 里的类型定义一致。
- **命令、路径、字段名、环境变量以代码为准**。本 README 里出现的每条命令、目录结构、字段名和环境变量都应当在仓库里核对过；改代码时要同步改这份文档。
- **不要留下占位内容**。文档里不写「以后补」这类空洞的句子；拿不准的先去读代码。
